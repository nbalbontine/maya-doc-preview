How we define the product, from evidence to Jira

This page shows how the Maya Agentic Platform team keeps its product definition in one place. The product definition is the briefs, market problems, personas, requirements and stories that explain why we build something and what it must do. Instead of scattered docs, boards and chat threads, it lives as one linked set of documents where every change is reviewed and recorded.

Overview

The problem

Product knowledge is spread across documents, Miro boards and chat. When a design test or customer call changes what we believe, finding and updating everything that depends on it takes longer than the fix itself.

The approach

A single dossier: a numbered chain of documents where each one is built from the ones before it. Requirements point back to market problems, and market problems point back to real evidence.

The safeguard

When something upstream changes, the documents downstream are flagged for review, not silently rewritten. Automation drafts and routes the work; people decide what changes, and every decision is logged.

Key terms

Artifact
One document in the chain, such as the brief, the personas or the PRD. Numbered 01–09 at initiative level and 01–04 per epic.
Dossier
The full set of artifacts for one initiative, kept together in one repository.
Evidence
Raw input: interview notes, usability findings, customer feedback. Filed once, never edited afterwards.
Review
The only way to change an artifact after it is first written. Each concern is accepted, rejected or deferred, and the decision is logged.
Flag (drift)
A marker placed on a document when something it was built from has changed, so its owner knows to check it.
Epic
A slice of the PRD that is planned and delivered on its own, broken down into use scenarios, stories and Jira tickets.

Diagram 6 showed the decision in plain language. This is the identical change — the usability finding updating personas, workflow map, touchpoint map and PRD — as it runs through GitHub: which branch it lands on, who GitHub asks to review because of which files were touched, and what has to be true before the merge button unlocks.

    PM->>Branch: Commit edited 04-07 artifacts + review-log entry
    PM->>PR: Open PR "Update personas/PRD after usability finding"
    PR->>PR: CODEOWNERS matches the changed file paths
    PR->>Lead: Auto-request review (owns 01-brief.md, 07-prd.md)
    PR->>Dev: Auto-request review (optional, feasibility)
    Dev->>PR: Comment only - feasible, no objection
    Lead->>PR: Approve - principle change accepted
    PR->>Prot: Check required approval from code owner
    PR->>Prot: Check drift-check status is green
    Prot->>PM: Merge button unlocks
    PM->>PR: Merge (squash) into main
    PR->>Branch: main is current, next drift-check clears downstream flags

This is the target configuration, not a claim it's on everywhere today

CODEOWNERS and required-reviewer branch protection are what we recommend turning on per repo. Until they are, the review-log.md entry is the actual contract — GitHub then hardens it so a merge can't skip that step by accident.

Takeaway The file you touch decides who GitHub makes you convince — not everyone can approve every merge.
